# native 工具按需加载设计 评审

## 评审目标与范围

- 目标: `docs/design/2026-10-23-native-deferred-tools-design.md`（suga 仓库，分支 `docs/native-deferred-design`，候选提交 `10ecc9bf`）
- 修订版本: Draft 0.1
- 评审者: Claude（监督会话；设计由 suga 子 agent 撰写，评审者未参与撰写）
- 日期: 2026-10-23
- 排除项: 实现代码（尚无）；子 agent registry（设计已明确不改）。

## 输入与方法

- 第 1 轮全量通读候选设计。
- 对照代码：`pkg/agentcore/tools/visibility.go:247-295`（`ListTools` 现在把已加载的延迟工具**立即**按名追加进工具表；`ExecuteTool` 对未加载的延迟工具会加载并以错误返回其 schema，提示模型“再调用一次”）。
- 依据：评审报告合同、SR1301、SR1409（未投产、可回滚、无出机器动作 → 单轮合并轴评审）。

## 验收标准

- 设计回答任务的 6 个问题；默认行为变化有可回退开关；
- 段内加载的工具在本段内**可用**（设计结论 5 的承诺）；
- 不破坏前缀缓存的既有收益；不影响子 agent、ACP、sugasdk。

## 发现

### F1 [HIGH] “段边界才入表、段内靠执行层放行”依赖模型调用未声明的工具，可行性未证实

- 证据: 设计 §3 方案表与结论 4、5：`tool_search` 命中后“工具表不变”，模型按结果文本里的参数清单“可立刻按正确参数调用”，执行由 `Visibility.ExecuteTool` 放行。但模型发出原生工具调用的前提是该工具出现在请求的 `tools` 声明里：主流 provider 的模型通常不会调用未声明的函数，部分 API 还会在严格模式下或对历史中引用未声明工具的 `tool_use` 报错。现有 MCP 路径之所以可用，正是因为 `ListTools` 在加载后立即把工具加入工具表（`visibility.go:247-267`）。
- 影响: 若模型无法在段内调用未声明工具，结论 5 的“本段内加载的工具立即可调用”不成立：工具要等到下一次换段（长会话中可能是几十轮之后）才真正可用；对 `memory`/`recall`/`session_search` 这类“低频但关键”的工具（Q6 默认延迟）尤其致命——模型想用而用不了，只会反复 `tool_search` 或放弃。这是核心验收的失败（`CORE_BLOCKING`，类别 `BUG`）。
- necessity proof:
  - core_acceptance: “段内加载的工具在本段内可用”（设计结论 5，Q4 方案的前提）。
  - necessary_causal_chain: 工具不在 `tools` 声明 → 模型不发出该工具的原生调用（或 API 拒绝）→ 工具在本段不可用 → 关键低频工具在长会话中段失效。
  - minimal_owner: 本设计 §3（加载时机）。
  - deletion_alternative: PASS——删掉“段边界入表”、沿用现有“立即入表”即可保证可用，代价是每次加载失效一次前缀缓存（设计 §3 已算账）。
  - scope_effect: 不新增模块；可能新增一个常驻代理工具（见建议 B）。
- 建议: 在批准前把 Q4 改为“由实施前探针决定”的分支，并写清两个可选方案：
  - A. **探针先行**：实施第一步用真实 provider（command-code 的 Claude、opencode-go/command-code 的 deepseek 与 glm）验证两件事——①工具 schema 只出现在消息文本里时，模型能否发出该工具的原生调用；②历史中含未声明工具的 `tool_use` 时 API 是否接受。两者都成立才采用“段边界入表”。
  - B. **常驻代理工具**（探针不成立时的默认）：工具表里常驻一个很小的 `tool_call`（或复用 `tool_search` 增加 `call` 动作）`{name, arguments}`，段内已加载的延迟工具经它调用，执行、审批、hook、trace 按真实工具名走；到段边界再把已加载工具原生入表。工具表在段内始终不变，缓存收益保住，可用性也不依赖 provider 行为。
  - 无论哪种，`immediate` 仍保留为回退开关。
- disposition: `CORE_BLOCKING`

### F2 [MEDIUM] 新增“需要低频工具”的评测任务应作为默认开启的前置条件

- 证据: Q8 建议新增 1 个评测任务；Gate 3 才看通过率。现有评测没有任何 run 覆盖延迟加载（设计已指出 `deferred_tools` 恒 0）。
- 影响: 默认开启（Q1）后若可用性有问题，只能在实施后发现。
- 建议: 计划中把“新增评测任务 + 4 个难版 `--repeat 3` 对照 + F1 的探针”列为把默认值切到开启之前必须通过的 Gate；在此之前实现可以先以默认关合入。
- disposition: `CORE_CORRECTIVE`

## 安全核对（SR1301）

- 鉴权 / 资源归属: 已核对——延迟工具执行仍经同一审批、hook 与只读模式（设计 §3 表第 2 行）；代理方案（F1-B）须按真实工具名走审批，不能绕过。
- 注入防护 / 秘密 / 入参校验: 不适用（不新增外部输入面；代理工具的 `arguments` 仍经目标工具自身的参数校验）。

## 覆盖缺口与限制

- 未实际运行 F1 所述的 provider 探针；结论基于主流 provider 的工具调用约定与现有代码行为。
- 计算收益的口径沿用设计与固定前缀报告，未复核。

## 结论

BLOCKED：F1 为 `CORE_BLOCKING`（段内可用性依赖未证实的 provider 行为）。按 F1 建议修订 Q4（探针决定 + 代理工具兜底）后可提交用户批准；SR1409 低暴露度，修订后不再另开评审轮。

## 剩余风险与后续

- 代理工具方案会让模型多学一种调用方式，需在新增评测任务中观察是否被正确使用。
- MCP 是否同步改为段边界入表（Q5）应等 native 方案在评测中稳定后再定。
