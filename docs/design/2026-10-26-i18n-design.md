## 背景

suga 的 gcli 参数帮助大多已经是英文，但 chat 提示、审批、状态、CLI 成功/错误输出仍以中文为主。扫描（排除 Go 注释和 `_test.go`）得到约 1,245 行生产 Go 代码含中文；测试也包含约 3,094 行中文文本。中文不仅是终端文案：预算/截止提醒、工具结果说明、交接与系统提示词会进入模型请求；`[已经人工批准执行]`、`out:` ref、`tool_search`、`[收工检查]` 等还具有事实标记或文本解析意义。

因此本设计不主张全局替换中文，而是把人类 UI（A）与模型提示/工具协议（B）隔离，先做可回滚的 UI 词条层。依赖调研基于 `github.com/gookit/i18n@v1.3.0` 源码（模块自身要求 Go 1.21，依赖 `gookit/ini/v2`）。

## 范围与非目标

### 范围

- 在配置中新增全局语言键，并让 `suga config get/set/unset/list` 认识它。
- 为第一阶段 A 类人类界面提供 `zh` 与 `en` 词条和统一门面。
- 明确模型可见文字、trace/transcript、ACP、stream-json、Gofer hooks 的稳定边界。
- 为文案 key、参数、缺失词条、测试和后续文档/模型阶段建立可执行验收。

### 非目标

- 本任务不改业务代码、不加依赖；本设计批准后仍需另写计划并经批准才能实施。
- 第一阶段不翻译 B 类系统提示、工具 description、工具结果、预算/截止/交接/收工指令；不改变模型行为或请求前缀。
- 不翻译 JSON 字段、工具名、命令名、错误 code、ACP/stream-json/Hook 事件名，也不把模型回答强行翻译。
- 不自动翻译 `docs/design`、`docs/research`、历史 CHANGELOG；不把 `lang-rules.yaml`（编程语言规则）误当作 UI 语言设置。
- 不提供运行中切换语言；语言在进程启动时解析，修改配置后重启生效。
- 不在本批扩展到任意地区化（日期、数字、货币、时区、复数规则）；`zh`/`en` 只是 UI 语言，locale formatting 另立设计。

## 总体方案

### 1. 配置键与优先级

推荐新增**顶层 `lang`**，而不是 `ui.lang`：

```yaml
lang: auto # auto | zh | en；默认 auto
```

取舍：`ui.lang` 能表达“只影响终端界面”，但当前目标还包含 CLI、审批、用户可见错误和后续文档选择，且项目没有稳定的 `ui` 配置组；顶层 `lang` 更短、与 `SUGA_LANG` 一致，也为文档版本/未来非 chat UI 留出空间。若用户希望严格把模型/文档语言分开，可在后续另设 `docs.lang`/`model.lang`，不复用 `lang` 改变既有语义。

第一版取值严格为 `auto`、`zh`、`en`。实现可接受 `zh-CN`/`en-US` 作为兼容别名并立即归一为 `zh`/`en`，但 `config get` 输出规范化值；不承诺其它地区标签。

解析优先级（高到低）：

1. `SUGA_LANG` 非空值（显式环境覆盖，非法值启动时报 `SUGA_LANG must be auto, zh or en`）。
2. 配置 `lang`（`suga config set lang en` 写入 active config；`get` 展示 effective value、source 和规范化值）。
3. 缺省等同 `auto`。

`auto` 规则：

- Unix/macOS 依次读取 `LC_ALL`、`LC_MESSAGES`、`LANG`（空值/`C`/`POSIX` 视为非中文）。locale 前缀为 `zh` 或包含 `Hans`/`CN`/`SG` 等简体中文标识时选 `zh`，其余选 `en`。
- Windows 不依赖 `LANG`（通常不存在）：使用 Windows 用户 locale（优先 `GetUserDefaultLocaleName`，失败再用 system locale）；`zh-*` 选 `zh`，其余选 `en`。实现放在 `internal/i18n/locale_windows.go`，不调用 shell。
- 未知/不可读 locale 选 `en`，避免把未知环境误判成中文；现有中文用户应设置 `lang: zh` 固定行为。默认 `auto` 的兼容影响是：中文系统仍为中文，非中文系统从旧版中文变为英文，需在升级说明中明确并给出一行回退配置。

语言在启动初始化后固定。`SUGA_LANG` 不写回 YAML；`config unset lang` 后回到 `auto`。不新增 `--lang`，避免 flag/env/config 三套相互覆盖；若后续有一次性 CLI 需求再另立决策。

### 2. gookit/i18n 接入与门面

**Capability decision：`THIN_ADAPTER`。** 现有 i18n 依赖和配置/启动装配足够；只需要一个小的 `internal/i18n` 门面隔离第三方 API、解析 locale、记录缺词条与提供类型安全的调用入口，不需要在 `pkg/agentcore` 新建能力层。

建议结构（实施阶段）：

```text
internal/i18n/
  i18n.go              # Options, Language, Catalog, T(key,args...)
  locale.go            # auto 解析（公共环境逻辑）
  locale_windows.go    # Windows locale API
  locale_unix.go       # LC_ALL/LC_MESSAGES/LANG
  catalog/
    en.ini
    zh.ini
```

`catalog/*.ini` 用 `//go:embed` 嵌入；初始化：

```go
//go:embed catalog/*.ini
var catalogFS embed.FS

l := gookiti18n.NewWithFS(catalogFS, "catalog", selected, languages).Init()
l.FallbackLang = "en"
```

细节：

- 使用 `NewWithFS` + `FileMode`（默认），每种语言一个 `catalog/<lang>.ini`；不使用默认全局 `Init/Std/Reset`，避免测试和宿主并发共享可变状态。
- gookit `Tr(lang,key,args...)` 在语言不存在、key 不存在或消息为空时会尝试 `FallbackLang`，仍不存在则返回 key；门面先用 `HasKey(selected,key)` 记录一次缺失告警，再调用 `Tr`。英文词条也缺失时返回 key，并带 key/语言的诊断日志，不把中文硬编码作为隐式第三语言。
- 参数优先使用 `ReplaceMode` 和命名占位符（例如 `approval.allow = Allow {tool}? [y] Yes [N] No`），门面接受 `map[string]interface{}` 或统一的小参数结构；避免 `%!s` 等 `fmt.Sprintf` 格式错误。若采用 SprintfMode，必须给每个参数写格式测试。
- gookit 的 `I18n` 数据结构、语言 map 和 `ini.Ini` 没有锁；`Init`/`Load*`/`NewLang` 等写操作只在启动阶段执行，返回的 Catalog 后只读。门面不提供运行时加载/切换；若未来必须热切换，需在门面外层用 `RWMutex` 交换完整实例，不能直接改现有实例。
- gookit `Init` 加载失败会 panic；suga 门面初始化应在装配边界捕获/转换为启动错误（catalog 是内嵌资源，发布包缺文件属于不可恢复构建错误），而不是在 chat 回合中 panic。
- `pkg/agentcore` 不能 import `internal/i18n`。第一阶段把 UI 翻译调用放在 `internal/chat`、`internal/cli`、必要的 host `internal/personal`；agentcore 的工具/API错误、描述和模型文字保持原文。若第三阶段需要 B 类翻译，应该在 agentcore 内定义与模型协议无关的 message provider/资源能力，另出设计并更新 layering 白名单，不能偷偷跨层。

初始化时机：读取配置 → 解析语言 → 创建 `Catalog` → 传入 `internal/wiring`/chat/CLI 的运行时；所有 goroutine、ACP session、后台任务共享只读 Catalog。`config` 命令本身若只读配置，可使用一次性的 config-only catalog；错误时仍输出稳定英文诊断，不能因语言 catalog 阻塞 `config get`。

## 词条组织

### 文件和 key

- 资源位置：`internal/i18n/catalog/en.ini`、`internal/i18n/catalog/zh.ini`，随二进制发布，不读取用户可写目录，防止配置/工作区内容伪装 UI 词条。
- key 使用小写点分层、稳定语义而非中文原文：`chat.approval.allow`、`chat.command.unknown`、`chat.status.turn_finished`、`cli.config.written`、`cli.error.invalid_argument`。命令名、工具名、参数名作为 `{tool}` 等值传入，不进 key。
- 一条消息一个 key；不要把一个长段通过字符串拼接拆成不可翻译的片段。参数使用命名占位符，并在 key 注释或 Go 类型中记录必需参数。
- `en.ini` 是完整 canonical key 集；`zh.ini` 必须有同一 key 集。每个 locale 可有少量 UI 专属 key，但不得让运行时依赖隐式 key；计划阶段应决定是否禁止额外 key，建议禁止。

### 校验和缺失

- 单测加载两份 catalog，比较 key 集完全相等；参数占位符集合也必须相等（例如 `{tool}`、`{scope}`）。
- 启动时只校验内嵌资源；开发/CI 再跑一次 catalog parity 检查。失败包含语言、key、缺失/多余占位符。
- 选中语言缺词条：警告一次，回退英文；英文也缺时返回 key 并警告/计数。不能静默回退中文，因为英文用户会得到混杂语言且无法发现翻译缺失。
- key 在日志/trace 中只作为诊断，不把 warning 注入模型消息；缺词条不改变 ACP/stream-json 结构。

## 关键流程

1. **启动**：加载 config/env → 按优先级解析 `lang` → locale `auto` 归一为 `zh`/`en` → 加载内嵌 INI → 校验 key/占位符 → 构造只读 Catalog。
2. **chat/CLI UI 输出**：调用 `internal/i18n.T(key,args)` → 选中语言词条 → 缺失时英文 fallback → 写入终端/UI。工具名、快捷键、路径、错误里的动态值原样保留。
3. **审批**：仅把人看到的询问/确认说明本地化；输入字符 `y/n/a/d/u/p`、规则文件路径、工具名和审批结果机器状态不变。审批写入 trace/transcript 的事实注记不在第一阶段翻译。
4. **模型请求**：第一阶段不经过 Catalog 改写 prompt、工具 schema、工具结果、budget/deadline/injected/handoff 文本；若一条字符串同时属于 UI 和模型，先拆调用点或整体保留原文。
5. **ACP/stream-json/Gofer**：生成协议对象时保留稳定字段和事件名；只在纯终端渲染边界调用 Catalog。外部客户端选择自己的语言时，不能依赖 suga 翻译 ACP payload。
6. **配置变更**：`suga config set lang en` 只编辑 YAML，后续新进程生效；当前进程不热切换。`get/list` 显示规范化 effective value 与 source，不泄露环境中的其它敏感变量。

## 架构

```text
config.yaml / SUGA_LANG / system locale
              │
              ▼
      internal/config (read + validate lang)
              │
              ▼
 internal/i18n.Resolve + Catalog (embed.FS, zh/en, fallback en)
              │ read-only
     ┌────────┼──────────┬──────────────┐
     ▼        ▼          ▼              ▼
 internal/  internal/  internal/      internal/
 chat       cli        personal       wiring(host UI)
     │          │          │              │
     └──────────┴──────────┴──────────────┘
              terminal / human UI

 pkg/agentcore ── no dependency on internal/i18n in phase 1
   model prompt, tool schema/result, trace facts, ACP/stream-json shapes stay stable
```

装配约束：`internal/wiring` 可以持有/传递 UI Catalog，但 `pkg/agentcore` 不接收它；模型可见文本必须继续由现有 prompt/tools 代码产生。若传递 Catalog 会导致 wiring → agentcore edge，视为设计违规，应用 host-side renderer 或另出 capability。

## 分阶段与验收

### 阶段 1：A 类界面

范围：chat prompt/状态/`:help`/`:usage`/审批询问、CLI 纯展示、用户可读错误、剪贴板/终端提示。`zh` 词条逐字保持当前行为（除非拆分本来就修复了拼接问题）；`en` 覆盖同一 key 集。机器 token 和文本协议保持稳定。

验收：

- `suga config set/get/unset/list lang`、`SUGA_LANG` 覆盖和 auto（Unix + Windows 解析单测）通过，非法值报错且不写配置。
- catalog key/占位符 parity 通过；缺 key 的测试能失败；缺选中语言回退英文并有一次 warning。
- 现有 ptye2e/单测在隔离 `lang: zh` 下保持预期；新增 `lang: en` chat/approval/config 场景验证英文。
- 至少一个测试走真实装配路径（`Wiring.Open`/`chat.Run`/构建出的二进制），不是只测门面。
- `go test`、`go vet`、`staticcheck`、gofmt 及 Linux ptysmoke 按项目规则验证；新英文交互反向验证：临时去掉 Catalog 调用时英文断言必须失败。

### 阶段 2：suga-guide 英文版

范围：`skills/suga-guide` 面向用户的安装、配置、命令和故障排查参考；设计/研究/历史文档不自动生成。建议资源按版本随 skill 发布：当前 suga 版本使用同版本英文 guide，缺失时回退到中文同版本；不能把“最新版”英文文档展示给旧二进制。

验收：链接/命令/配置 key 与中文版 parity；`lang=en` 的向导入口选择英文，`lang=zh` 选择中文；版本号、代码块、工具名、配置字段保持一致；文档 lint/链接检查通过。具体“按语言释放哪一版”需在发布计划确认：建议 tag 同步发布 `guide/<version>/en` 与 `zh`，未翻译版本明确标注 fallback。

### 阶段 3：B 类模型文字（另立设计）

范围：系统提示、工具 description/result、预算/截止/交接、收工检查、审批事实注记等。必须先清点模型可见协议，再决定是否允许按 lang 改变。`pkg/agentcore` 不直接依赖 internal facade；可选方案是 agentcore 自有资源能力或调用方提供稳定的 message catalog，需重新审 layering。

真实模型评测：至少一个真实 provider、同一模型/温度/任务集，`zh` 与 `en` 对照各 `--repeat 3`；覆盖普通文件任务、需审批工具、预算/截止收尾、`recall/session_search`、长会话换段和交接。比较通过率、工具选择/参数错误、审批语义、token、延迟、`cache_read_tokens`/命中率，分“段内同 context”和“换段/压缩/交接”桶；以现有 long-session 基线判定不退化。若真实 provider 未验证，不得宣称 B 阶段完成。

## 测试策略

- **语言解析单测**：`t.Run` 覆盖显式 `SUGA_LANG`、config、auto、空/非法值、Unix `LC_ALL > LC_MESSAGES > LANG`、Windows locale；使用 `t.TempDir`/`t.Setenv`，不触碰真实 `~/.suga`。
- **catalog 单测**：key 集、参数集、fallback、缺失 warning 去重、并发只读；使用 `github.com/gookit/goutil/x/assert`。
- **配置真实路径**：通过 `suga config set/get/unset/list` 和隔离 `SUGA_HOME` 验证，不只调用 `ParseConfigValue`。
- **UI 路径**：chat/CLI 真实装配至少一条；现有中文文本测试显式固定 `lang=zh`。新增英文场景固定 `lang=en`，不依赖运行机器 locale。
- **ptysmoke/ptye2e**：现有场景在独立 SUGA_HOME 写 `lang: zh`，保持中文断言；新增英文场景覆盖 banner、审批、状态和 `:help`。脚本开头清空自己的工作目录/SUGA_HOME，结果并入最终计数。Windows 无 pty 时写好但由 Linux 监督运行，不能在本机声称通过。
- **协议回归**：ACP、stream-json、hooks golden/contract 测试比较字段和事件，不比较可本地化 UI 文案；trace 中的稳定事实标记/工具名继续按原值断言。
- **反向验证**：暂时让英文路径绕过 Catalog 或删一条 key，英文断言/parity 必须失败；暂时将 UI catalog 调用替换成中文，英文 pty 场景必须失败。

## ACP、stream-json 与 Gofer 侧边界

| 输出 | 第一阶段处理 |
|---|---|
| JSON-RPC method、request/notification 名、字段名、ID、error code、`stopReason`、tool name、MCP server/tool 标识 | 绝不翻译；这是接口契约 |
| ACP 的权限 action、工具调用状态、session/update 的结构化 kind/role | 结构不变；若字段中有纯展示 `title/description`，第一阶段仍保持现状，待 ACP 客户端语言协商后另议 |
| stream-json 的 event type、JSON key、usage/error_kind、trace schema、机器可解析的 reason | 绝不翻译；message 若被下游解析则保持稳定英文/现值 |
| Gofer hooks 的事件名、argv、JSON key、`SessionStart/UserPromptSubmit/PostToolUse/Stop/SessionEnd/Interrupt`、来源/注入标记 | 绝不翻译；Gofer 侧不得依赖中文 UI 文案 |
| chat/CLI 终端 renderer 的 prompt、审批、状态、帮助和人类错误 | 可翻译，调用 Catalog |
| ACP/stream-json 客户端自己展示的文本、模型最终回答 | suga 不翻译；客户端/模型负责语言 |

## 决策

- **D1：键名用顶层 `lang`**。相比 `ui.lang` 更覆盖 CLI/审批/文档选择；模型语言另议，不把顶层键偷换成 B 类开关。
- **D2：默认 `auto`，只支持规范化 `zh`/`en`**。中文 locale 中文，其它和未知 locale 英文；显式 `lang: zh` 给现有中文用户稳定回退。
- **D3：`SUGA_LANG > config.lang > auto`，进程启动时固定**。环境覆盖不写回 config，不增加 `--lang`。
- **D4：`THIN_ADAPTER` 的 `internal/i18n` + embed.FS + 实例 API**。不使用 gookit 全局状态；`pkg/agentcore` 不依赖 internal。
- **D5：`en` 为 fallback，缺词条告警**。避免英文界面混入中文；key parity 把缺失变成 CI 错误。
- **D6：阶段 1 仅 A，D 类先拆分/保持稳定，B 单独设计**。控制模型行为、缓存前缀和长会话评测风险。
- **D7：接口契约优先于本地化**。ACP/stream-json/Gofer 机器字段和稳定文本不翻译，展示层再本地化。

## 待确认事项

1. 是否接受顶层 `lang` 而非 `ui.lang`？本稿推荐 `lang`。
2. 是否接受 `auto` 默认对非中文系统显示英文（中文用户可显式设 `lang: zh`）？若必须完全保持旧行为，默认应改为 `zh`，但会降低英文社区首次体验。
3. 是否接受第一阶段 `en`/`zh` 两种语言、区域别名仅归一化而不做 locale formatting？
4. Windows auto 是否以用户 locale 为准（推荐）而非系统 locale？企业环境的集中策略可能希望后者。
5. ACP 的权限请求 `title/description` 是否要在第二阶段跟随客户端语言协商？本设计第一阶段保持稳定。
6. 阶段 2 guide 的发布目录和版本回退策略由 release 计划确认；本设计建议同 tag 同步版本。
7. 是否批准阶段 3 单独出 B 类模型文字设计，并把真实 provider/缓存分桶评测作为进入条件？
8. 阶段 1 完成后，`lang: en` 的用户仍会在工具结果、transcript 和部分提示里看到 B 类中文（如 `[已经人工批准执行]`、预算/截止提醒、ref 展开指引），系统提示里的中文片段也可能让模型倾向用中文回复。英文推广是否以阶段 1 为准就够，还是要把阶段 3 提前、或在阶段 1 后先做一个“模型侧英文最小集”（只换用户最常看到的几条注记与提醒，配真实模型对照评测）？

## 风险与回滚

| 风险 | 缓解 | 回滚 |
|---|---|---|
| auto 误判 locale，现有中文用户看到英文 | 显式 `lang: zh`；启动时打印/manifest 记录 resolved language；Windows API 单测 | 删除/禁用 language 初始化，默认回到原中文输出 |
| 漏翻/参数不一致 | en/zh key 与 placeholder parity；缺失 warning；英文 smoke | 回退到同一 key 的英文/原文，保留 catalog 不影响协议 |
| gookit 全局状态或并发写导致竞态 | 只用独立实例；Init 前完成加载；运行期只读；不提供热切换 | 移除门面调用，保留硬编码原文；不影响会话数据 |
| UI 词条误进入模型，改变行为/缓存 | A/B/D 清单；agentcore 分层守卫；阶段 1 不改 prompt/tools | 按提交阶段回退；B 文字独立提交/开关 |
| pty/ACP/Gofer 文本断言断裂 | zh 固定回归；协议字段不翻译；英文新场景和反向验证 | `SUGA_LANG=zh` 或回退 UI facade |
| 引入 i18n 依赖增加模块/许可证风险 | 只采用 v1.3.0，审核其 MIT 许可和 transitive deps；本任务不改 go.mod | 未批准前不加依赖；实施提交可整批回退 |

## 人工 Gate
