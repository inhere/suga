# ptysmoke

在伪终端（PTY）里驱动真实的 `suga` 二进制做端到端冒烟，覆盖单元测试测不到的终端行为：raw/cooked 切换、提示符重绘、回合中提前输入、Ctrl-C、确认交互等。仅 Linux/macOS（依赖 Python `pty`）；Windows 控制台行为需人工确认。

| 文件 | 作用 |
|---|---|
| `fakellm.py` | OpenAI 兼容的 SSE 假模型：`--mode tool` 先返回 `shell_exec` 调用、工具结果后回复文本；`--mode text` 只回复文本；`--mode edit` 依次返回 `file_grep`、`file_edit` 调用再回复；`--mode memory` 先 `shell_exec` 再 `memory` add（用户消息含“直接”时跳过 shell）；`--mode refs` 依次返回 `file_refs`（`--ref-name` 对一个文件 `--ref-file`）与 `file_refs`（同一名字对一个目录 `--ref-dir`）调用再回复；`--mode adddir` 依次返回 `file_read`（`--read-path`）、`file_write`（`--write-path`、`--write-body`）调用再回复（用户消息含“只读”或“只写”时只发其中一条调用）；`--delay` 控制每次响应前的等待；`--prompt-tokens` 设定上报的输入用量；`--no-usage` 完全省略 usage，供估算场景使用；`"stream": false` 的请求（如 compaction 摘要）回一个 JSON 响应；多线程服务（流式与非流式请求走不同连接）；`--background` 让 tool 模式的 shell_exec 带 `background: true`（收到 `[background task` 开头的通知或提醒只回文本）；`--lines N`/`--wide M`（text 模式）把回复换成 N 行、每行补齐到 M 列的长回复（超宽行用），`--chunk N` + `--chunk-delay S` 把流式文本切成 N 字符一块、每块之间等 S 秒（供“回复还在流式时正在输入插话”的屏幕断言）；`--fail-first N` 前 N 个请求回 HTTP 503，`--break-first M` 随后 M 个流只发一半回复就断开连接（重试冒烟用）；`--fail-from N [--fail-count M]` 从第 N 个请求起失败 M 次（M<=0 表示此后一直失败，中断回合冒烟用）。每个请求在 stdout 打一行 JSON：`model` 是请求的模型字段，`user` 是最后一条 user 消息，`seen` 是请求里每条消息的简短标记（`user:<前 40 字符>`、`a:file_write`、`tool:edited …`），`tail` 是最后几条消息的 `{"role", "text"}`（回合中插话能在这里看出来） |
| `ptydrive.py` | PTY 驱动库：`mark()` 后只检查新输出、`until()` 等待模式出现再输入、`drain()` 把新输出读进缓冲供 `contains()` 判断、`check()` 记录结果、`resize(cols, rows)` 改窗口大小（发 SIGWINCH）；还带一个最小 VT 屏幕模型 `Screen`（处理 CR、LF、退格、`ESC[K`、`ESC[2K`、`ESC[nA/B/C/D`、`ESC[nG`，按窗口宽度折行、宽字符算两列，其余转义跳过），`feed(raw)` 后 `screen_lines()` 得到各行（去掉结尾空格）——用于断言“这段话到底落在哪一行、有没有残行”，而不只是 grep 字节流；`input_row(session, cols)` 取输入行那一行（最后一行以 `❯ `/`↳ ` 开头的行，去掉结尾空格），用来判断输入行是空的还是还留着文字；自带 `python3 -c "import ptydrive; ptydrive._self_test()"` |
| `chat_rules.py` | 审批规则：allow 命中不询问、deny 命中拒绝且回合继续、规则优先级、命令前缀/目录 scope、`a/d` 与 `u/p` 跨进程写回、trace/manifest 诊断，以及命令/路径控制字符清洗；反向验证见脚本说明。 |
| `chat_approval.py` | 现成场景：开场模型、❯ 提示符、写工具确认（y/n/a/Ctrl-C）、提示符处单次 Ctrl-C 只提示、连按两次退出（汇总与续接命令）、非 TTY 拒绝；窗口设为 100 列，并检查输入行按终端宽度折行（90 个字符仍在同一行；去掉 `SetSize` 调用时该检查会失败），以及运行中把窗口改到 60 列后编辑器按新宽度排版（用宽字符在行尾的填充空格判断；去掉 resize 监听时该检查会失败）；输入行有文字（`abc`）时 Ctrl-C 只清空输入行——不出现“再按一次 Ctrl+C 退出”、chat 不退出、屏幕模型看到那一行只剩提示符，接着键入的文字自成一行（wll1）；审批提问处即便行上有文字，Ctrl-C 仍是取消该问题（`SetCtrlCClearsLine` 只给提示符与回合的读取）；回合中提前输入不放行分 `chat.steering` 开/关两组跑：开着时该行算插话（显示 `[插话] y`，随后的问题仍要下一行作答）、关着时该行被问句的读取丢弃且不算插话 |
| `chat_budget.py` | 预算交互：小 token 预算的状态行、一次提醒与软收尾；session 已用尽时不再调用模型；真实/估算用量、`estimate: off`、插话返回后新 turn 预算重置与未配置回归；退出后用 `suga inspect trace --json` 检查 scope/reason/estimated。反向验证见脚本 docstring |
| `chat_edit.py` | `file_grep` 免确认、`file_edit` 确认显示原文/改为、确认后文件被修改、两次 Ctrl-C 退出 |
| `chat_undo.py` | 写入/编辑/删除快照、`:checkpoints`/`:undo` 确认与补全、冲突/force、shell 边界、回滚通知、trace snapshot attrs、附加目录/cwd 变化、无快照和终端文本清洗；脚本 docstring 列出反向验证 |
| `chat_idle.py` | 空闲整理：`context.idle_after: 2s` + 小 `context_window`，回合时长超过 idle_after 时回合中不触发；回合结束后出现“✦ 空闲整理中…”与“✦ 已整理上下文：X → Y token”；之后输入正常；整理进行中输入会抢占它（无成功提示、回合照常回答）；`suga inspect trace` 可见 schedule 事件与 reason=idle 的分段 |
| `chat_observe.py` | 观测进入 trace：配置一个 hook 命令（UserPromptSubmit 注入上下文），在审批提示处停 1.2s 再答 y，退出后检查 `suga inspect trace --json`：SessionStart / UserPromptSubmit（注入字符数）/ Stop 三个 hook 事件，shell_exec 的 `approval=user` 与等待时间，回合 context 事件计入 hook 注入 |
| `chat_retry.py` | 模型重试：`retry` 配成 200ms 级等待，假模型先回 503、再断一次流、再完整回复；检查 chat 显示 503 重试提示与“将重新输出”的断流提示、之后完整回复，`suga inspect trace --json` 的 model 事件 `retries=2`、`retry_reason=stream broken` 与等待时间 |
| `chat_interrupt.py` | 中断回合的回放（suga-y0sk）：假模型 `--fail-from 3 --fail-count 3`＋`retry.max_attempts: 3`，回合先跑 `file_grep`、再 `file_edit`（target.txt 已改动），随后应答请求连续 503 到回合 failed；检查 chat 显示重试与 `Error: … request failed after 3 attempts`、磁盘上的改动确实在；再发一句后，模型请求（fakellm 的 `seen` 摘要）里重新带有那次 `file_grep`/`file_edit` 调用与结果、顺序正确、并带中断小结，`suga inspect trace` 有 failed/后续 completed 两个回合、`suga inspect export` 里有 `suga.turn_interrupted` 条目。反向验证见脚本 docstring |
| `chat_danger.py` | 危险删除：`tools.approval: auto`、HOME 指向临时目录，假模型调用 `rm -rf ~`；检查仍会询问并显示危险原因、答 `y` 被拒且临时目录还在、答 `yes` 才执行且目录被删，trace 两条 shell_exec 事件带 `danger` 与审批来源 |
| `chat_tasks.py` | 后台任务：假模型以 `background: true` 启动 `sleep 1.5; echo TASK_DONE` 后直接回复；检查回合先结束、任务结束后空闲的 chat 被自动唤醒并显示通知（退出码与输出），trace 有带 `task_id` 的 shell_exec 与 `task` 事件；再用 `suga run` 启动 `sleep 30`：提醒一次（两个回合）、退出时终止任务并在 stderr 注明、不等满 30s |
| `chat_onboarding.py` | 首次运行与 CLI 上手：version/help 无副作用、init/force 备份与 `.env` 保留、显式 `SUGA_CONFIG` 保护、config/path 与离线 models 的输出/JSON/无网络检查；反向验证见脚本说明 |
| `chat_model.py` | `:model` 查看模型与 thinking/上下文窗口/输出上限，切换到第二个模型后用 fakellm 请求日志和 `suga inspect trace --json` 检查下一回合与 `--resume` 仍使用它；反向验证见脚本 docstring |
| `chat_watch.py` | watch 与后台 Stop hook：假模型启动监听 `a.txt` 的 watch，脚本把文件改到命令失败，空闲 chat 被通知唤醒（`exit 0 -> 3`），再写入相同内容只运行不通知，trace 的任务事件有 runs/changes；`hooks.stop_background` 下 hook 睡 3 秒后 block，第一轮后立即输入第二句：hook 从不收到 Interrupt，第一个 Stop 任务被第二个终止，block 以通知唤醒 chat，随后的 Stop 带 stop_hook_active。`--no-stop-background` 用于反向验证 |
| `chat_agent.py` | 子 agent：假模型调用 `agent` 工具，子 agent（按系统提示词识别）grep 一次后交报告。同步默认 `summary` 不显示 `  ·` 逐条行而显示调用数/耗时汇总，`sync-full` 覆盖 `full` 逐条行为；trace 的 agent 事件带子会话 id 与 stop=final；Ctrl-C 打断慢的子 agent 时被中断的回合显示“已中断本轮”（不出现原样的 `context canceled`）、chat 正常退出且子会话不停在 running；后台：立即返回任务 id，子 agent 结束后以报告通知唤醒空闲 chat 并检查汇总。`--agents-off` 用于反向验证 |
| `chat_memory.py` | 未污染会话直接写记忆并显示“已记住”；`shell_exec` 置污染（`memory.taint_tools`）后写记忆询问（显示范围/类型/标题/正文），y 写入、n 拒绝、a 本会话不再问；条目落在 SUGA_HOME 的 files 后端 |
| `chat_spinner.py` | “思考中…”等待行：本场景显式不带 `NO_COLOR`（该行只在有色终端显示）并关掉 `chat.steering`（steering 开时回合中输入行常驻，等待行不画，避免争同一行），假模型 `--delay 2` 让提示可见；检查首个回合前不显示、等待模型首个消息时出现（带已用秒数）、工具调用行替换它、工具结果后再次出现、答案前最后一条提示已被 `ESC[2K` 清除（看原始缓冲，`text()` 会剥掉 ANSI）；同时还覆盖终端标题（`chat.terminal_title`）：启动时先 `ESC[22;0t` 保存再把标题设为 `suga · <短名称>`，首条消息后标题带上会话标题，Ctrl-D 退出时标题清空再 `ESC[23;0t` 恢复；另一个 `chat.spinner: false` / `chat.highlight_input: false` / `chat.terminal_title: false` 的会话完全不显示该行、不加背景、不写标题序列 |

编写新场景的要点：

- 断言只看 `s.mark()` 之后的输出（`s.until(pattern, m)`、`s.contains(pattern, m)`），不要在整个缓冲里找——前面轮次的输出会让检查误判。
- 等待预期提示出现后再输入：chat 在确认询问前会清除未读输入，提前写入的回答会被丢弃（`chat.steering` 开着时提前写的那行先算回合中的插话，因为回合一直在读输入行）。
- raw 模式下回车是 `\r`，Ctrl-C 是 `\x03`，Ctrl-U 是 `\x15`。
- 以结果行（如 `⎿ ok: ...`）判断工具是否执行，确认提示本身也会回显命令。
- 每轮结束以状态行（`tokens · `）为准再进入下一步；场景自己负责启动和停止假服务，不要依赖外部后台进程。
- 工作目录在本仓库内（有 `.gofer/tracker`），`write_home` 固定 `memory.project.backend: files`，冒烟不会调用真实 gofer。
