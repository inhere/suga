# ptysmoke

在伪终端（PTY）里驱动真实的 `suga` 二进制做端到端冒烟，覆盖 raw/cooked 切换、提示符重绘、回合中提前输入、Ctrl-C、确认交互等终端行为。Python `scripts/ptysmoke` 仅在 Linux/macOS 运行，是完整场景与行为依据；Windows 用 Go `test/ptye2e` 通过 ConPTY 运行精简的高风险回归（审批后重绘、本地命令、未知冒号文本、多行粘贴）。

**迁移中**：Python 脚本正逐批迁到 Go（`github.com/gookit/gopty/ptytest`，Linux 与 Windows ConPTY 同一套），入口 `make smoke-go`（`go test -tags ptye2e -count=1 ./test/ptye2e/`），共享的假模型是 `test/ptye2e/fakellm_test.go`（`fakellm.py` 的 Go 版，目前支持 text/tool/edit/memory/display/adddir/empty-final/refs/loop/loop-edit/loop-fail/preferred/agent/session/nudge 模式与 `--fail-from/--fail-count`，其余模式随后续批次迁入；按请求记录的 `seen` 摘要对应 Go 的 `fakeRequest.Seen`）。已迁移并删除的脚本：`chat_edit` `chat_diff` `chat_render` `chat_theme` `chat_idle` `chat_retry` `chat_observe` `chat_commands`（第 1 批），`chat_rules` `chat_undo` `chat_danger` `chat_tasks` `chat_model` `chat_shortname` `chat_sanitize` `chat_empty_final`（第 2 批），第 3 批：`chat_adddir` `chat_adddir_cmds` `chat_bang` `chat_budget` `chat_delivery` `chat_interrupt` `chat_loop_guard` `chat_refs` `chat_resume`（Go 测试 `TestChatAddDir` `TestChatAddDirCommands` `TestChatBang` `TestChatBudget` `TestChatDelivery` `TestChatInterrupt` `TestChatLoopGuard` `TestChatRefs` `TestChatResume`；`TestChatDelivery` 的“退出时丢弃排队消息”一步在 Unix 发 SIGTERM，在 Windows 由辅助进程向 chat 的控制台发 CTRL_BREAK，见 `terminate_*_test.go`）。对应 Go 测试 `TestChatEdit` 等同名；场景共用的 `write_home`/`wait_port`/`isolate_ws`/`trace_events`/`check_answered_prompt` 在 `ptydrive.py`。后续批次：`chat_pretool`、`chat_deferred_native`、图片类、英文 UI（`chat_i18n_en`）与 `chat_approval`（Go 测试 `TestChatApproval`，含窗口宽度/改宽与假模型的 `ToolOnce`）、`preferred_tools`（`TestPreferredTools`，stdio MCP 夹具用测试二进制自启动，假模型 `preferred` 模式）、`chat_resume_cwd`（`TestChatResumeCwd`）、`chat_agent`（`TestChatAgent`，子 agent 的同步汇总/逐条、Ctrl-C、后台、失败与状态行场景）、`chat_session_message`（`TestChatSessionMessage`，两个 chat 互发到跳数上限）、`chat_memory`（`TestChatMemory`，记忆写入询问的 y/n/a 与 files 后端条目）已迁完删除；`chat_onboarding`（`TestChatOnboarding`，首次运行 init/--force 与离线 config/models）、`chat_nudge`（`TestChatNudge`，收工提示的两条规则与 workspace 规则文件）与 `chat_watch`（`TestChatWatch`，监听唤醒与后台 Stop hook）已迁完删除。输入行断言读 VT 屏幕（`test/ptye2e/vtscreen_test.go`，`ptydrive.Screen` 的 Go 版），不 grep 字节流：ConPTY 会重绘整行，Linux pty 只写新文字。

| 文件 | 作用 |
|---|---|
| `fakellm.py` | OpenAI 兼容的 SSE 假模型：`--mode tool` 先返回 `shell_exec` 调用、工具结果后回复文本；`--mode text` 只回复文本；`--mode edit` 依次返回 `file_grep`、`file_edit` 调用再回复；`--mode memory` 先 `shell_exec` 再 `memory` add（用户消息含“直接”时跳过 shell）；`--mode refs` 依次返回 `file_refs`（`--ref-name` 对一个文件 `--ref-file`）与 `file_refs`（同一名字对一个目录 `--ref-dir`）调用再回复；`--mode adddir` 依次返回 `file_read`（`--read-path`）、`file_write`（`--write-path`、`--write-body`）调用再回复（用户消息含“只读”或“只写”时只发其中一条调用）；`--mode display` 依次返回带行范围的 `file_read`、两行命令的 `shell_exec` 与 `update_plan` 再回复（工具调用行显示冒烟用）；`--delay` 控制每次响应前的等待；`--prompt-tokens` 设定上报的输入用量；`--no-usage` 完全省略 usage，供估算场景使用；`"stream": false` 的请求（如 compaction 摘要）回一个 JSON 响应；多线程服务（流式与非流式请求走不同连接）；`--background` 让 tool 模式的 shell_exec 带 `background: true`（收到 `[background task` 开头的通知或提醒只回文本）；`--lines N`/`--wide M`（text 模式）把回复换成 N 行、每行补齐到 M 列的长回复（超宽行用），`--chunk N` + `--chunk-delay S` 把流式文本切成 N 字符一块、每块之间等 S 秒（供“回复还在流式时正在输入插话”的屏幕断言）；`--fail-first N` 前 N 个请求回 HTTP 503，`--break-first M` 随后 M 个流只发一半回复就断开连接（重试冒烟用）；`--fail-from N [--fail-count M]` 从第 N 个请求起失败 M 次（M<=0 表示此后一直失败，中断回合冒烟用）。每个请求在 stdout 打一行 JSON：`model` 是请求的模型字段，`user` 是最后一条 user 消息，`seen` 是请求里每条消息的简短标记（`user:<前 40 字符>`、`a:file_write`、`tool:edited …`），`tail` 是最后几条消息的 `{"role", "text"}`（回合中插话能在这里看出来） |
| `ptydrive.py` | PTY 驱动库：`mark()` 后只检查新输出、`until()` 等待模式出现再输入、`drain()` 把新输出读进缓冲供 `contains()` 判断、`check()` 记录结果、`resize(cols, rows)` 改窗口大小（发 SIGWINCH）；还带一个最小 VT 屏幕模型 `Screen`（处理 CR、LF、退格、`ESC[K`、`ESC[2K`、`ESC[nA/B/C/D`、`ESC[nG`，按窗口宽度折行、宽字符算两列，其余转义跳过），`feed(raw)` 后 `screen_lines()` 得到各行（去掉结尾空格）——用于断言“这段话到底落在哪一行、有没有残行”，而不只是 grep 字节流；`input_row(session, cols)` 取输入行那一行（最后一行以 `❯ `/`↳ ` 开头的行，去掉结尾空格），用来判断输入行是空的还是还留着文字；另外还有各场景共用、从 `chat_approval.py` 迁来的 `write_home`（写 SUGA_HOME/config.yaml）、`wait_port`、`isolate_ws`、`trace_events`、`check_answered_prompt`；自带 `python3 -c "import ptydrive; ptydrive._self_test()"` |
| `chat_steer.py` | 回合中插话与“只中止本轮”（`chat.steering`）：工具运行中输入并回车，插话送达**同一回合**（假模型请求日志里插话紧跟工具结果之后、trace 有 `steer_delivered`、本回合只有一个 turn 事件、状态行显示插话次数）；模型已给出最终回复时到达的插话成为紧接着的下一回合（trace `steer_returned` 的 `completed_untaken`/`next_turn`）；Esc 与单次 Ctrl-C 只中止本轮（显示“已中断本轮，N 条插话已放回输入行”、chat 仍在、插话回到输入行且回车才运行），两次 Ctrl-C 退出；审批提问期间键入的是答案而不是插话；工具运行中粘贴两行（`ESC[200~第一行\n第二行ESC[201~` 带标记）不在行断处提交、回车后作为**一条**插话送达同一回合（假模型请求日志里是一条 user 消息，trace 一条 `steer_delivered`），并用最小 VT 屏幕模型断言回合中的输入行画在模型输出下方；`chat.steering: false` 回到旧行为；另有 `clear` 场景：回合中在输入行上留字（`这行要被清掉`）后按 Ctrl-C，只清空该行——不出现“已中断本轮”、不产生插话、也没有新的模型请求，屏幕模型看到那一行只剩 `↳`，随后键入的句子独自送达**同一回合**（假模型请求日志里没有被清掉的那句），行空时再按 Ctrl-C 仍只中止本轮（wll1）；`suga send --steer` 场景：工具运行中从外部跑真实 CLI（gofer 投递的方式），首个响应 `steered`、插话到达**同一回合**的下一次请求（假模型请求日志）、`--steer --wait` 在该回合结束**之前**返回 0（尚无回答与状态行）、Esc 中止的回合让等待的发送方退出码 3 且插话回到输入行、第九条返回 `queue_full`（退出码 1）、空闲时退化为排队（响应 `queued`，打印“未插入当前回合，已排队”）；`followup` 场景（suga-8pug）：模型回答期间在 `↳ ` 行键入后按 `Tab`，输出区显示 `[排队] …（本轮结束后发送）`、该行离开输入行、当前回合的请求日志里没有它、trace 里也没有 steer 事件（它不是插话），本回合结束后它作为下一回合的 prompt 自动发送并显示“（已发送）”。反向验证见脚本 docstring |

- `make smoke-pty-go`：运行 `test/ptye2e` 的 Go `ptytest` 场景；Windows 使用 ConPTY，Linux/macOS 使用 Unix pty。若宿主不允许 ConPTY，测试框架会跳过并打印原因。

```bash
make smoke-chat
# 或指定二进制与工作目录
python3 -I scripts/ptysmoke/chat_steer.py --bin tmp/smoke/suga --work tmp/smoke-steer --keep
```

编写新场景的要点：

- 断言只看 `s.mark()` 之后的输出（`s.until(pattern, m)`、`s.contains(pattern, m)`），不要在整个缓冲里找——前面轮次的输出会让检查误判。
- 等待预期提示出现后再输入：chat 在确认询问前会清除未读输入，提前写入的回答会被丢弃（`chat.steering` 开着时提前写的那行先算回合中的插话，因为回合一直在读输入行）。
- raw 模式下回车是 `\r`，Ctrl-C 是 `\x03`，Ctrl-U 是 `\x15`。
- 以结果行（如 `⎿ ok: ...`）判断工具是否执行，确认提示本身也会回显命令。
- 每轮结束以状态行（`tokens · `）为准再进入下一步；场景自己负责启动和停止假服务，不要依赖外部后台进程。
- 工作目录在本仓库内（有 `.gofer/tracker`），`write_home` 固定 `memory.project.backend: files`，冒烟不会调用真实 gofer。
- UI 语言由场景自己的 SUGA_HOME 决定：`write_home` 默认写 `language: zh`（与真实用户一致），英文场景传 `language="en"`；不要依赖 `make` 里的环境变量，脚本要能单独跑。`SUGA_LANGUAGE` 优先级高于配置，会盖掉这个固定值。
- 端口不要写死：`--port` 默认 `0`，`resolve_port(args.port, span)` 在启动假模型前取一个空闲端口（`span` 是场景从 base 派生的 `base+1…base+span` 个数，整段都保证可绑）；显式 `--port N` 仍按 N。
